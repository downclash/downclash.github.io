v2rayN 配置 Git 代理：HTTPS、SSH 与安全恢复

v2rayN 配置 Git 代理应先确认 HTTPS 或 SSH 远程地址。用单次命令测试 HTTP 代理，再按仓库范围保存设置；核对 URL 匹配、认证和绕过变量，并保留可恢复的原配置。

Git 如何使用 v2rayN 的代理？

HTTPS 仓库先用一次性 git -c 指定 v2rayN 的实际 HTTP 端口，验证能读取远程引用，再决定是否写入仓库配置。SSH 地址不读取 Git 的 http.proxy，需要另查 SSH 连接路径。

  1. 确认远程地址是 HTTPS 还是 SSH。
  2. 对 HTTPS 做一次读取测试，并在客户端日志确认请求确实进入代理。
  3. 需要持久配置时先记录原值，再使用 --local 限定到当前仓库；退出客户端后按记录恢复。

继承的 no_proxy / NO_PROXY 可能绕过代理，不能仅凭命令有输出就断定经过了 v2rayN。

网页能打开代码仓库而 git fetch 失败，常见原因是浏览器和 Git 使用了不同网络入口。Git 的 HTTP(S) 传输可以使用代理；SSH 传输由另一套程序处理。配置适用范围见 Git 的 http.proxy 说明。开始前先确认远程地址协议，再调整代理，避免用 HTTP 设置反复修理 SSH 连接。

确认 Git 远程地址使用 HTTPS 还是 SSH

在本地仓库的远程设置中查看地址：https://… 属于 HTTP(S)，git@host:owner/repo.git 或 ssh://… 属于 SSH。查看时注意地址可能含用户名或令牌，不要原样公开。以下示例使用 Git 项目的公开 HTTPS 仓库，仅用于验证读取连接，不会推送代码。

确保 v2rayN 活动节点可用，并记录真实 HTTP 监听端口。本文用 10809 作示例，改为实际端口；代理入口属于运行 Git 的环境。Remote SSH、WSL 或容器中的 Git 不能直接假定能连接宿主机的回环端口。

用一次性 Git 代理参数测试 HTTPS 仓库

对明确的目标主机，使用 -c 给这次 Git 调用传入代理。下例把代理限制到 GitHub 的 HTTP 配置匹配范围：

git -c http.https://github.com.proxy=http://127.0.0.1:10809 ls-remote https://github.com/git/git.git HEAD

如果命令有输出但客户端没有对应请求，先检查 Git 进程继承的 no_proxy / NO_PROXY。libcurl 的绕过名单说明指出，匹配目标的名单即使在指定代理时也可能绕过它。在 Bash 或 Zsh 中，可只为这次诊断清空绕过名单，测试结束后父 shell 的原值不变：

no_proxy= NO_PROXY= git -c http.https://github.com.proxy=http://127.0.0.1:10809 ls-remote https://github.com/git/git.git HEAD

这是 Bash / Zsh 写法，不能原样粘贴到 PowerShell；在其他 shell 中应采用其单进程环境设置方式。确认日志后再判断代理路径，不要为了测试长期删除组织内网需要的绕过规则。

命令正常时应输出 HEAD 对应的对象 ID 和引用名称，同时客户端出现该连接。它只读取远程引用，不证明大文件传输、私人仓库权限或后续推送一定正常。公共仓库能读而私人仓库返回认证错误时，应转查账号权限与凭据，而不是继续换代理。

如果显式配置仍表现异常，需要在自己的设备上检查目标匹配到哪项代理。不要打印整份 Git 配置，因为其中可能包含额外认证头、令牌或内部仓库地址。以下先查询目标匹配到的代理，再单独检查当前仓库通用代理键的来源。结果若含凭据仍须隐藏；没有匹配项时，查询可能以非零状态结束，并不代表仓库损坏：

git config --get-urlmatch http.proxy https://github.com/git/git.git
git config --local --show-origin --get-all http.proxy

仅给当前 Git 仓库设置代理

先在当前仓库记录原有 http.proxy 的值与是否存在，再写入本地作用域。下面设置影响此仓库的 HTTP(S) 操作，不会自动修改其他仓库，也不会为 SSH 增加代理：

git config --local --get-all http.proxy
git config --local http.proxy http://127.0.0.1:10809

执行前确认没有需要保留的多值配置；若已有复杂规则，应通过配置编辑器保存原段落再调整。全局、系统、仓库、URL 匹配项以及远程专用代理可能同时存在，简单设置一个通用键未必覆盖所有更具体的规则。Git 配置文档列出了这些作用域与匹配方式。出现不符预期的行为时，按目标查询结果判断，不要只重复写 --global。

完成后对原来失败的操作复测：先读引用，再按实际需要 fetch，最后才处理需要身份认证的推送。每次只调整一种配置来源，有助于确认是哪项产生效果。

SSH 仓库为什么不受 http.proxy 影响？

SSH 通常由 OpenSSH 或 Git 配置的其他 SSH 程序发起连接，它不通过 Git 的 HTTP 传输。因此 HTTP 代理测试成功，不能证明 git@… 已经配置代理。SSH 需要核对主机、端口、密钥、SSH 配置以及所用转发工具的能力。

如果服务支持 HTTPS，可以在明确了解认证差异后自行选择 HTTPS 工作流；不要为了代理问题盲目重写所有远程地址。若继续用 SSH，应依照 SSH 与托管平台的官方文档配置，不能把某个系统专用的 netcat 命令原样复制到其他系统。TUN 也只能解决流量入口的一部分问题，不能修复错误密钥或仓库权限。

清除新增代理或恢复仓库原设置

使用一次性 -c 无需清理持久配置。若本地代理键原先不存在且只有本教程新增的一条值，可在同一仓库执行：

git config --local --unset http.proxy

若原来已有代理，应恢复事先记录的值，而不是直接删除；URL 专用键也要在原作用域分别恢复。恢复后重新查询目标匹配项并测试。不再监听的本机端口会让后续 Git 操作失败，这通常是残留配置，而非仓库损坏。无需重建仓库、删凭据或重装 Git。

Git 代理常见问题

HTTPS 仓库需要另外配置 https.proxy 吗？

Git 文档中的 http.proxy 用于 HTTP(S) 传输，不能因为远程地址是 HTTPS 就臆造另一个配置键。先查询目标实际匹配的代理，再检查 URL 专用项、远程配置和环境变量。

curl 能通过代理，Git 的 SSH 地址为什么仍失败？

curl 的 HTTP 测试只验证了那条请求。git@… 由 SSH 发起连接，不会自动读取 Git 的 HTTP 代理设置；需要分别核对 SSH 主机、端口、密钥、授权和可达路径。

关闭客户端后 Git 一直连接 127.0.0.1，怎么恢复？

检查原来在哪个作用域添加了代理。若本教程新增的仓库代理原先不存在，只移除这条本地键；若原先已有值，恢复记录的原值。不要为此删除仓库或清空所有 Git 配置。
