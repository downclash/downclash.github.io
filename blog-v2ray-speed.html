V2Ray 连接与速度排查：节点、DNS、系统代理和 TUN

按节点、认证、DNS、路由和流量接管逐层排查 v2rayN、v2rayNG 的连接与速度问题，区分延迟与带宽，并用可复现检查验证每次设置修改。

“连接慢”和“连接不上”需要不同的检查。先确定问题发生在客户端启动、节点握手、DNS、流量接管，还是目标服务，再修改对应设置。以下步骤适用于 v2rayN、v2rayNG 等工具的日常排查；菜单名称会随版本变化，底层字段应以实际核心文档为准。

记录一组可复现的对照

  1. 记下系统、客户端版本、当前核心及版本、节点、网络类型、代理模式和故障时间。
  2. 选一个需要验证的目标网站或应用，再选一个预期可直连的本地服务，保持测试对象一致。
  3. 先测试系统正常直连是否可用，再启用一个已导入的节点，记录实际加载结果和核心日志。
  4. 每次只改变一个条件，例如节点 A / B，或 Wi-Fi / 移动数据，重复相同请求。

不要同时更换节点、DNS、协议与 TUN 设置；否则即使恢复，也难以判断是哪项产生作用。测速可能消耗流量，应按需要测试少量候选节点。

延迟、带宽与线路选择

TCP 延迟主要反映服务器端口建立连接所需时间；客户端的实际连接测试会按其测试方式检查更多链路；文件下载速度反映指定目标、时段与连接方式下的吞吐。三者不能互相替代，某个节点延迟更低，也可能因拥塞而下载更慢。

日常网页可比较首屏打开是否稳定；视频可比较持续播放与缓冲；远程桌面可比较交互延迟与抖动。保持相同设备、网络和目标，先测试两个可用节点，再按自己的实际任务选择。

地区距离与线路名称可以作为筛选信息，但不能单独证明质量。BGP、CN2、专线等标签不能替代实际测量；更换客户端或把协议改成某个名称，也没有固定的提速百分比。协议与传输必须先兼容服务端。

DNS 与路由核对

节点服务器本身需要解析、目标网站需要解析、规则也可能在匹配时触发解析。这些请求可能走不同路径。先从日志确认失败的是哪个域名，以及发往哪个 DNS，再判断是否需要调整。

  • 节点域名解析失败：检查建立代理前可使用的解析路径，避免解析服务器必须经由尚未建立的同一代理。
  • 目标域名解析失败：核对当前配置中的解析器、DNS 分流与出站路由；仅替换一个公共 DNS 地址不一定能修复可达性。
  • 内网域名异常：保留公司或本地网络需要的解析器与路由，不能让内网名称全部交给公网解析器。
  • 规则命中不符：核对规则顺序、最终出站，以及所用 GeoIP / Geosite 或规则集是否存在、是否适用于该核心。

V2Fly、Xray、sing-box 的 DNS 与路由字段并不相同。按配置文档查实际核心的语法，调整后重启相关连接，并重新运行同一测试。

系统代理、TUN 与 VPN

桌面端先确认应用有没有进入客户端

系统代理是给支持它的应用提供本机代理地址，并不保证终端、游戏或所有桌面程序自动使用。如果浏览器可用而某个应用没有任何连接日志，先检查该应用的代理配置；确需覆盖更多应用时，再按客户端说明启用 TUN。

TUN 开启后检查接管范围与冲突

TUN 涉及虚拟接口、系统路由和 DNS。若开启后连内网也失效，先关闭 TUN 作一次对照，并核对其他 VPN、虚拟机与容器网络。sing-box 文档明确提示自动路由需避免回环，部分严格路由设置也可能影响其他软件，因此不宜套用来源不明的整段配置。

Android 同时核对 VPN 权限与应用名单

确认 v2rayNG 已获系统 VPN 连接授权，再核对分应用代理是“只代理所选应用”还是“绕过所选应用”。若仅锁屏后停止，复现时观察 VPN 状态和进程是否仍在运行，再按设备系统设置允许所需的后台运行。

只有大文件或某类 UDP 应用异常时，才进一步核对服务端 UDP 支持、路由与链路 MTU。修改 MTU 前记录原值，按项目建议逐项验证；不存在适用于所有网络的一组万能数值。

修改与恢复

每次保留原配置并写下一条记录：“改了什么、在哪个网络测试、哪个目标恢复、是否出现新的问题”。升级前备份自定义规则，升级后重新核对所用核心和默认行为。

不用代理时，通过客户端清除系统代理并关闭 TUN / VPN 后再退出。如果异常退出导致直连也不可用，检查系统是否残留指向已停止本机端口的代理设置；恢复后再重新打开客户端。

证书校验失败应核对时间、服务器名称、证书链和配置来源。不要把关闭证书校验当作提速或长期修复。提供诊断日志时隐藏订阅 token、UUID、密码和个人访问记录。
